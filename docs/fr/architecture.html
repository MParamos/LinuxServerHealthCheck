Architecture Technique

La philosophie centrale de LSHC est le découplage absolu et l'immuabilité. Ci-dessous se trouve une analyse du cycle de vie du système, conçue pour les programmeurs et les administrateurs système souhaitant auditer ou étendre le framework.

1. Cycle de Vie d'Exécution

L'orchestrateur principal (AssemblyScript.sh) ne possède aucune logique de surveillance intrinsèque. Il agit comme un pipeline aveugle qui délègue le travail aux modules vérifiés.

    L --> M[Ajoute au Corps du Rapport]

    M --> N[Charge le Modèle HTML de Pied de Page]
    N --> O[Chiffrement et Envoi via SMTP Mailx]

2. Isolation de la Mémoire (Sous-shells)

Le plus grand risque dans les scripts Bash modulaires est la collision de variables. LSHC prévient cela en encapsulant l'exécution de chaque module dans un environnement enfant :

# Extrait de AssemblyScript.sh
( 
    source "src/modules/$module/module.sh" 
    envsubst < "src/modules/$module/template.html" 
) >> "$REPORT_BODY"

En utilisant des parenthèses ( ... ), un fork du processus bash est créé. Toute variable déclarée ou modifiée dans module.sh est détruite à la fin du bloc, gardant la mémoire de l'orchestrateur vierge.

3. Résolution Dynamique à la Compilation (Build-Time)

Afin d'éviter les images Docker surchargées, le Dockerfile inclut un analyseur de dépendances intelligent. Il installe strictement et uniquement les commandes requises par les modules actifs.

sequenceDiagram
    participant D as Dockerfile
    participant C as ModulesInReport.conf
    participant M as src/modules/*/packages.txt
    participant A as APT (apt-get)
    
    D->>C: Lit la liste des modules non commentés
    C-->>D: Ex. performance, security_audit
    D->>M: Concatène et déduplique les paquets des modules actifs
    M-->>D: Ex. lm-sensors, hdparm, nmap
    D->>A: apt-get install -y [paquets]
⚠️ Persistance des Bibliothèques : L'image Docker étant immuable, si vous désactivez un module, les bibliothèques qu'il a installées persisteront dans l'image actuelle du conteneur. Pour les purger définitivement, la meilleure pratique absolue est de reconstruire une image propre en exécutant docker compose build --no-cache.

4. Confidentialité et Base de Données Locale Air-Gapped

Afin d'assurer une confidentialité absolue de l'infrastructure, LSHC utilise un conteneur MariaDB dédié (linuxserverhealthcheck_db) qui n'expose aucun port externe au réseau hôte. Les modules stockent leurs métriques historiques directement ici, et se purgent cycliquement via leur prune.sh (ou effacent complètement lorsqu'ils sont désactivés). Aucune métrique ne quitte jamais le serveur hôte.

5. Bonnes Pratiques de Suppression (Graceful Deletion)

Si vous souhaitez supprimer définitivement le dossier d'un module, ne le supprimez pas brusquement. Cela empêcherait le script sync_modules.sh de trouver et d'exécuter le fichier cleanup.sql du module, laissant des tables historiques orphelines occupant un espace inutile dans la base de données interne.

Le flux architectural correct pour une suppression complète est le suivant :

  1. Commentez ou supprimez le nom du module dans le fichier ModulesInReport.conf.
  2. Exécutez un rapport manuel (ex. ./RunManualHealthCheck.sh). L'orchestrateur détectera la désactivation du module et déclenchera la destruction de ses tables dans la BD locale.
  3. Supprimez physiquement le dossier du module dans src/modules/.
  4. Exécutez docker compose build --no-cache && docker compose up -d pour recréer le conteneur principal sans les dépendances APT du module supprimé.

6. Immuabilité et Recréation Obligatoire (Zero-Trust)

LSHC est conçu selon le principe strict de l'Infrastructure Immuable. Le conteneur principal n'autorise pas le rechargement à chaud (hot-reloading) des fichiers, pas même du fichier de configuration .env.

Pourquoi cette décision ? Si des fichiers de l'hôte étaient mappés directement à l'intérieur du conteneur en direct (volumes de configuration), un script malveillant ou un attaquant ayant un accès non privilégié au serveur physique pourrait altérer le fichier .env ou les scripts des modules. Lors de la prochaine exécution de Cron, le conteneur (qui a un mode privilégié) exécuterait ce code injecté en tant que root.

En forçant la cuisson des fichiers dans l'image (ou l'injection native des variables uniquement au démarrage), nous comblons complètement cette vulnérabilité. C'est pourquoi toute modification de code ou de variable nécessitera toujours de recréer le conteneur (docker compose up -d) ou de le reconstruire (docker compose build), transformant le système en un bunker Zero-Trust.
