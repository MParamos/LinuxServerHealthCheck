Technical Architecture

The core philosophy of LSHC is absolute decoupling and immutability. Below is a breakdown of the system's lifecycle, tailored for programmers and sysadmins wishing to audit or expand the framework.

1. Execution Lifecycle

The main orchestrator (AssemblyScript.sh) possesses no intrinsic monitoring logic. It acts as a blind pipeline that delegates work to verified modules.

graph TD
    A[Cron Daemon / Manual Run] -->|Calls| B[AssemblyScript.sh]
    B --> E((Loop: Iterates over
Active and Inactive Modules))
    E --> F{check_module_integrity.sh}
    
    F -- Invalid / Corrupt --> H[Injects Error HTML]
    F -- Valid --> G[(Isolated Subshell)]
    
    G -->|Module absent in ModulesInReport.conf| I[Module deactivation, and prune.sh execution to clear its internal database tables]
    G -->|Module present in ModulesInReport.conf| J[Executes module.sh]
    
    J --> K[Exposes Module HTML Variables]
    K --> L[Injects Module template.html]
    L --> M[Appends to Report Body]
    
    H --> M
    I -.-> E
    M -.-> E
    
    M --> N[Loads HTML Footer Template]
    N --> O[Encryption and Dispatch via SMTP Mailx]

2. Memory Isolation (Subshells)

The biggest risk in modular Bash scripts is variable collision. LSHC prevents this by encapsulating each module's execution within a child environment:

# Snippet from AssemblyScript.sh
( 
    source "src/modules/$module/module.sh" 
    envsubst < "src/modules/$module/template.html" 
) >> "$REPORT_BODY"

By using parentheses ( ... ), a bash process fork is created. Any environment variable declared or mutated inside module.sh is automatically destroyed when the block ends, keeping the orchestrator's memory space completely pristine.

3. Build-Time Dynamic Resolution

To prevent bloated Docker images, the Dockerfile includes a smart dependency parser. It strictly installs only the base system commands required by the active modules.

sequenceDiagram
    participant D as Dockerfile
    participant C as ModulesInReport.conf
    participant M as src/modules/*/packages.txt
    participant A as APT (apt-get)
    
    D->>C: Reads uncommented module list
    C-->>D: E.g., performance, security_audit
    D->>M: Concatenates and deduplicates packages from active modules
    M-->>D: E.g., lm-sensors, hdparm, nmap
    D->>A: apt-get install -y [packages]
⚠️ Library Persistence: Since the Docker image is immutable, if you deactivate a module, the libraries it installed will persist inside the current container image. To permanently purge them, the absolute best practice is to rebuild a clean image by executing docker compose build --no-cache.

4. Privacy and Air-Gapped Local Database

To ensure absolute infrastructure privacy, LSHC utilizes a dedicated MariaDB container (linuxserverhealthcheck_db) that exposes no external ports to the host network. Modules store their historical metrics directly here, and purge themselves cyclically via their prune.sh script (or delete completely when deactivated). No metric ever leaves the host server.

5. Graceful Deletion Best Practices

If you wish to permanently delete a module's folder, do not delete it abruptly. Doing so prevents the sync_modules.sh script from finding and executing the module's cleanup.sql file, leaving orphaned historical tables occupying useless space in the internal database.

The correct architectural workflow for complete deletion is:

  1. Comment or remove the module's name in the ModulesInReport.conf file.
  2. Run a manual report (e.g. ./RunManualHealthCheck.sh). The orchestrator will detect the module's deactivation and trigger the destruction of its tables in the local DB.
  3. Physically delete the module's folder in src/modules/.
  4. Run docker compose build --no-cache && docker compose up -d to recreate the main container without the deleted module's APT dependencies.

6. Immutability and Mandatory Recreation (Zero-Trust)

LSHC is designed under the strict principle of Immutable Infrastructure. The main container does not allow hot-reloading of files, not even the .env configuration file.

Why this decision? If host files were mapped directly inside the container dynamically (configuration volumes), a malicious script or an attacker with unprivileged access to the physical server could alter the .env file or the module scripts. On the next Cron execution, the container (which runs in privileged mode) would execute that injected code as root.

By forcing files to be baked into the image (or natively injecting variables only during startup), we completely close that vulnerability. This is why any code or variable change will always require recreating the container (docker compose up -d) or rebuilding it (docker compose build), turning the system into a Zero-Trust bunker.
