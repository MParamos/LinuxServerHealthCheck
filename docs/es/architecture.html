Arquitectura Técnica

La filosofía central de LSHC es el desacoplamiento absoluto y la inmutabilidad. A continuación se desglosa el ciclo de vida del sistema, ideal para programadores y administradores de sistemas que deseen auditar o expandir el framework.

1. Ciclo de Vida de Ejecución

El orquestador principal (AssemblyScript.sh) no posee lógica de monitorización intrínseca. Se comporta como un pipeline ciego que delega el trabajo a los módulos verificados.

    B --> E((Bucle: Itera sobre
Módulos Activos e Inactivos))
    E --> F{check_module_integrity.sh}
    
    F -- Inválido / Corrupto --> H[Inyecta HTML de Error]
    F -- Válido --> G[(Subshell Aislado)]
    
    G -->|Módulo ausente en ModulesInReport.conf| I[Desactivación del módulo, y ejecución de prune.sh para borrar sus tablas de la base de datos interna]

    J --> K[Expone Variables HTML del Módulo]

2. Aislamiento de Memoria (Subshells)

El mayor riesgo en los scripts Bash modulares es la colisión de variables. LSHC previene esto encapsulando la ejecución de cada módulo en un entorno hijo:

# Fragmento de AssemblyScript.sh
( 
    source "src/modules/$module/module.sh" 
    envsubst < "src/modules/$module/template.html" 
) >> "$REPORT_BODY"

Al utilizar paréntesis ( ... ), se crea un fork del proceso de bash. Cualquier variable de entorno declarada o mutada dentro de module.sh se destruye automáticamente al terminar el bloque, manteniendo el espacio de memoria del orquestador completamente virgen.

3. Resolución Dinámica en Tiempo de Construcción (Build-Time)

Para evitar imágenes Docker pesadas, el Dockerfile incluye un analizador de dependencias inteligente. Solo se instalan en el sistema base los comandos estrictamente requeridos por los módulos activos.

sequenceDiagram
    participant D as Dockerfile
    participant C as ModulesInReport.conf
    participant M as src/modules/*/packages.txt
    participant A as APT (apt-get)
    
    D->>C: Lee la lista de módulos no comentados
    C-->>D: Ej: performance, security_audit
    D->>M: Concatena y deduplica los paquetes de los módulos activos
    M-->>D: Ej: lm-sensors, hdparm, nmap
    D->>A: apt-get install -y [paquetes]
⚠️ Persistencia de Librerías: Dado que la imagen Docker es inmutable, si desactivas un módulo, las librerías que instaló seguirán existiendo dentro de la imagen actual del contenedor. Para purgarlas definitivamente, la única y mejor práctica es reconstruir la imagen limpia ejecutando docker compose build --no-cache.

4. Privacidad y Base de Datos Local Air-Gapped

Para garantizar la privacidad absoluta de la infraestructura, LSHC utiliza un contenedor dedicado de MariaDB (linuxserverhealthcheck_db) que no expone puertos al exterior de la red de Docker. Los módulos almacenan su histórico métrico directamente aquí, y se purgan a sí mismos cíclicamente mediante su prune.sh (o se eliminan permanentemente si el módulo es desactivado). Ninguna métrica abandona jamás el servidor anfitrión.

5. Buenas Prácticas de Borrado (Graceful Deletion)

Si deseas eliminar la carpeta de un módulo permanentemente, no la borres de forma directa y brusca. Hacerlo impedirá que el script sync_modules.sh encuentre y ejecute el archivo cleanup.sql del módulo, dejando sus tablas históricas huérfanas en la base de datos interna ocupando espacio inútilmente.

El flujo arquitectónico correcto para el borrado total es:

  1. Comenta o elimina el nombre del módulo en el archivo ModulesInReport.conf.
  2. Ejecuta un informe manual (ej. ./RunManualHealthCheck.sh). El orquestador detectará la baja del módulo y ejecutará la purga y destrucción de sus tablas en la BD local.
  3. Elimina la carpeta del módulo físicamente en src/modules/.
  4. Ejecuta docker compose build --no-cache && docker compose up -d para recrear el contenedor principal sin las dependencias APT del módulo eliminado.

6. Inmutabilidad y Recreación Obligatoria (Zero-Trust)

LSHC está diseñado bajo el principio estricto de Infraestructura Inmutable. El contenedor principal no permite el hot-reloading (recarga en caliente) de archivos, ni siquiera del archivo de configuración .env.

¿Por qué esta decisión? Si se mapearan archivos del host directamente al interior del contenedor en caliente (volúmenes de configuración), un script malicioso o un atacante con acceso no privilegiado al servidor físico podría alterar el archivo .env o los scripts del módulo. En la siguiente ejecución del Cron, el contenedor (que tiene modo privilegiado) ejecutaría ese código inyectado como root.

Al forzar que los archivos se horneen en la imagen (o que las variables se inyecten de forma nativa solo durante el arranque), cerramos esa vulnerabilidad. Por eso, cualquier cambio de código o de variables requerirá siempre recrear el contenedor (docker compose up -d) o reconstruirlo (docker compose build), convirtiendo al sistema en un búnker de confianza cero (Zero-Trust).
